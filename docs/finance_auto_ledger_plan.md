# 재무 '자동 정리' 개편 기획 (10/27 대표 요청)

## 0. 한 줄 요약
**거래를 하나하나 분류하는 일을 없앤다.** 은행에 들어온 데이터는 전부 시스템이 먼저 '약식으로 100%' 정리해 첫 화면에 보여주고,
대표님은 시간 날 때 **특이한 것만 고치거나 '나중에 정하기'로 보낸다.** 확인이 덜 돼도 숫자는 처음부터 전부 반영된다.

## 1. 대표님이 정한 원칙 (이 문서의 기준)
1. 재무 섹션의 **첫 화면 = 자동 정리된 결과**. 계정과목 매칭·캠페인 매칭 같은 사전 작업이 필요 없다.
2. 숫자는 **항상 전체(100%)** 가 반영된다. 아직 확정 안 된 것도 빠지지 않는다(대신 얼마가 '자동'인지 표시).
3. 계정과목별로 **'상세보기'** → 거래를 보면서 그 자리에서 계정과목을 고치거나, **클릭클릭 → 저장**.
   빨리 못 정하겠으면 **'나중에 정하기'** 로 보내서 따로 처리.
4. **상쇄(결제↔취소·환불)** 는 사람이 누르지 않아도 자동으로 찾아서 **재무에서 빠진다**. 상쇄만 따로 모아서 보고, 필요할 때만 되돌린다.
   카드사 취소는 최대 1주일까지 걸린다.
5. **미수금·캠페인 매칭은 화면에 표시하지 않는다.** 데이터는 지우지 않는다(영업-재무관리 섹션을 대표님이 따로 기획).
6. 기존 원칙 유지: 선택 즉시 저장 금지(결정 버튼을 눌러야 저장) / 가짜 숫자 금지 / 급여는 개인별로 보이지 않음(월 합계만) / 데이터는 지우지 않음.

## 2. 새 첫 화면 `🏠 자동 정리` (재무캘린더 첫 메뉴)
```
[기간: 이번달 | 이번 분기 | 올해 | 전체]
┌ 매출 ₩… ┬ 비용 ₩… ┬ 영업이익 ₩… ┬ 순현금흐름 ₩… ┐   ← 전부 반영된 숫자
신뢰도 막대: ✓ 대표 확정 ₩…(n%) · ≈ 자동 분류 ₩…(n%) · ? 분류 대기 ₩…(n%)

계정과목        건수   합계      상태(확정/자동/대기)   [상세보기]
방문형 캠페인 매출 …
…
? 분류 대기(입금) / 분류 대기(출금)
♻️ 상쇄 보관함  n쌍 ₩…  (재무 미반영)        [상세보기]
🕓 나중에 정하기  n건                          [상세보기]
```
- **상세보기**: 거래처별 묶음(기본) / 원본 거래. 각 줄에 계정과목 드롭다운. 바꾼 줄만 모아 `💾 저장` 한 번.
  체크한 줄은 `⏭ 나중에 정하기`로 보낼 수 있다(숫자에는 지금의 자동 분류가 그대로 반영된 채로).
- **상쇄 보관함**: 자동으로 찾은 쌍 목록과 합계. 쌍마다 `상쇄 아님(복구)`. 합계는 전체 재무에서 제외.
- 기존 `🎯 재무 미션`은 이 화면으로 흡수(없어짐). 나머지 메뉴(대시보드·손익계산서 등)는 유지.

## 3. 자동 분류 엔진 (`auto_ledger.py`, 화면 계산용·DB는 바꾸지 않음)
위에서부터 먼저 맞는 것을 적용한다.
1. **대표 확정 분류**(is_auto_categorized=False) — 그대로 유지, 절대 덮어쓰지 않음.
2. **내부이체**: 적요에 회사 이름 + 반대편 거래(짝) 확인된 것만. 짝 없는 회사 이름 입금은 자동으로 내부이체 처리하지 않고 '분류 대기'에 둔다(10/22 대칭 원칙).
3. **상쇄**(§4).
4. **같은 거래처 이력**: 대표님이 이미 확정한 같은 적요(정규화) 거래의 분류를 따른다. 같은 적요가 여러 분류로 갈렸으면 따르지 않는다(확신 낮음).
5. **세금계산서·송금일정 연결 정보**가 있으면 그 분류.
6. **키워드 규칙**(`expense_breakdown.RULES`) — 확신 '높음'은 자동, '낮음/중간'은 자동 분류하되 '확인 권장' 표시.
7. (나중에, 선택) AI 분류 — Anthropic 크레딧이 살아날 때. 지금은 쓰지 않음.
8. 그래도 모르면 **분류 대기**(입금/출금 각각 한 줄). 숫자에는 들어가고 '?'로 따로 보인다.

* 정확도는 대표님이 확정한 거래로 **백테스트해서 숫자로 공개**한다(예: 같은 적요 이력이 있는 거래의 일치율).
* 10/27 DB 점검: 확정 411건 중 같은 적요가 2번 이상인 거래 258건, 그중 238건(92%)이 한 분류로 일관 →
  분류 없는 366건 중 187건(₩195.5M), 소액 자동분류 2,667건 중 279건이 이력만으로 바로 분류 가능.
* '단순경비(소액 자동분류)'(2,513건 ₩68.9M)는 DB 트리거가 붙인 임시 분류라 **자동 분류로 취급**해서 엔진이 더 세밀한 분류로 다시 본다.

## 4. 상쇄 자동 규칙 (확장)
같은 계좌 · 같은 금액 · 반대 방향. 가장 가까운 날짜·시각끼리 1:1로 짝짓는다.
| 단계 | 조건 | 처리 |
|---|---|---|
| ① 확실 | 같은 날, 10분 안 | 자동 상쇄(기존 규칙) |
| ② 카드 취소·환불 | 7일 안 + (입금 적요가 카드사·PG·페이·환불·취소이거나, 두 거래의 거래처가 같음) | 자동 상쇄 |
| ③ 의심 | 7일 안 같은 금액 쌍인데 ②의 근거가 없음 | 자동 반영 안 함(재무에 포함), 상쇄 보관함의 '의심'에 표시 |
* 내부이체로 짝이 확인된 거래는 상쇄 대상에서 제외(이중 처리 방지).
* 10/27 DB 점검(같은 계좌·같은 금액·반대 방향·7일 안): 182쌍 — 당일 103쌍, 1~7일 79쌍. 그중 카드·PG 성격 적요가 있는 쌍이 상당수. 실제 규칙 적용 결과는 구현 후 목록으로 확인한다.
* **삭제하지 않는다.** 은행 원본 거래는 뱅크다에서 다시 들어오므로(중복 방지 해시) 지우면 되살아날 수 있다. '삭제' 대신 **'상쇄 확정(재무 미반영, 기록 보관)'** 으로 정리한다.

## 5. 숨기는 것 (데이터는 그대로)
* Command Center의 받을 돈(미수금) 카드·수금 관련 표시, 메뉴 `CFO › Receivables`.
* 재무캘린더의 '송금일정/캠페인 연결' 표시(🔗), `매출 입금 ↔ 캠페인 연결` 편집기, 미수금 계산.
* 코드는 지우지 않고 화면에서만 뺀다(필요하면 환경변수로 다시 켤 수 있게). Campaign Margin 페이지는 그대로 둔다(대표님이 별도 판단).

## 6. 저장 구조
* 1단계: **DB 변경 없음**. 자동 분류·상쇄는 화면에서 계산. 대표님이 `저장`하면 기존 컬럼(`account_category_id`, `is_auto_categorized=False`)에만 쓴다.
* `나중에 정하기`·'거래처 규칙(앞으로 같은 거래처는 이 분류로)'을 저장하려면 새 테이블이 필요 → `migrations/`에 파일로 만들어 설명한 뒤 **사람이 적용**한 다음 코드를 배포한다
  (`fin_review_later`, `fin_merchant_rules` 예정. 없는 DB에서는 안내만 보이고 죽지 않게).
* 상쇄 '확정' 기록은 `bank_offset_overrides`(decision='offset')를 쓴다 — `20261019_bank_offset_confirm.sql` 적용 필요(미적용).
* ⚠️ staging과 운영은 같은 DB — 화면에서 `저장`을 누르면 즉시 실제 데이터가 바뀐다.

## 7. 개발 순서 (천천히, 단계마다 확인)
1. **엔진 + 백테스트**(읽기 전용): `auto_ledger.py`, 단위 테스트, 확정 거래 정확도 리포트, 상쇄 규칙 결과 목록.
2. **새 첫 화면(보기 전용)**: 숫자·신뢰도·계정과목별 표·상세보기·상쇄 보관함. 미수금/매칭 숨김.
3. **수정·저장**: 상세보기에서 계정과목 고쳐 한 번에 저장, 상쇄 '아님' 복구.
4. **나중에 정하기 + 거래처 규칙**(마이그레이션 후).
5. 손익계산서·Command Center·VAT 자료도 같은 엔진 숫자를 쓰게 정리, DB 트리거/백필(내부이체·소액 자동분류) 정리, 필요하면 AI 분류.
